What Is a Salesforce Change Set?

https://www.youtube.com/watch?v=MIYAiTIlWKQ
A **change set** is a collection of related changes (code, configuration, database scripts, etc.) grouped together for version control, review, or deployment.

In Salesforce, a Change Set is a deployment tool used to move metadata (customizations) from one Salesforce environment to another — typically from a Sandbox 
(development/testing) to Production. It is a point-and-click deployment method designed for admins and declarative developers who do not use code-based deployment 
tools like Salesforce CLI.

They are commonly used in:
    * Dev → QA → UAT → Production pipelines
    * Admin-led projects
    * Small to medium org deployments

Key Features of Salesforce Change Sets: 
1. **Metadata Deployment**: Change Sets allow you to deploy various types of metadata, including custom objects, fields, page layouts, workflows, 
                            validation rules, and more.
2. **Source and Target Environments**: You can create a Change Set in a source environment (like a Sandbox) and deploy it to a target environment (like Production).
3. **Dependency Management**: Change Sets automatically include dependencies, ensuring that all necessary components are deployed together.

1️⃣ Why Change Sets Are Used
    Organizations use Change Sets to:
    * Move configuration changes safely to production
    * Deploy custom objects, fields, flows, Apex classes, etc.
    * Maintain controlled releases
    * Track deployment status
    * Validate changes before deploying

Limitations of Change Sets
### ❌ No Version Control - They are manual and not Git-integrated.
### ❌ No Rollback - You cannot automatically revert a deployment.
### ❌ Manual Process - Not ideal for CI/CD pipelines.
### ❌ No Compare Feature - You cannot compare differences between orgs.
### ❌ Limited Automation - Not suitable for DevOps-heavy teams.


# 2️⃣ Types of Change Sets
    There are two types:
    ## 🔹 1. Outbound Change Set
    Created in the **source org** (usually Sandbox).
    It contains the components you want to deploy.
    ## 🔹 2. Inbound Change Set
    Appears in the **target org** (usually Production).
    Used to validate and deploy the components.

# 3️⃣ How Change Sets Work (Step-by-Step)
## Step 1: Create Outbound Change Set (Sandbox)
Go to:
> Setup → Deployment → Outbound Change Sets → New
* Give it a name and description
* Add components
    ***

        | ✅ Category               | ✅ Components You CAN Deploy              | 💡 Example                      |

        | ⚙️ **Automation**        | Flows, Workflow Rules, Process Builder   | Auto Email Flow                 |

        | ⚡ **LWC**               | Lightning Web Components                 | Account List LWC                |
        | 🧾 **Visualforce**       | VF Pages & Components                    | Legacy Page                     |
        | 🎨 **UI / Layout**       | Page Layouts, Lightning Pages, Tabs      | Custom Account Layout           |
        | 📊 **Reports**           | Reports, Dashboards, Report Types        | Sales Dashboard                 |
        | 📧 **Email**             | Email Templates, Letterheads             | Welcome Email Template          |
        | 🔗 **Relationships**     | Lookup, Master-Detail Relationships      | Account → Contact               |
        | 📦 **Custom Metadata**   | Custom Metadata Types, Settings          | App Configuration               |

        # ❌ 🚫 Not Supported (Important)
        | ❌ Cannot Deploy               | 💡 Reason                                                                              |
        | ----------------------------- | -------------------------------------------------------------------------------------- |

Important:
Change Sets move **metadata only**, NOT data.

##Step 2: Add the dependencies 
            - Apex Test Class 
            - Validation Rule
            - Custom fields
            - Fields used in rules
            - Email alerts/templates
            - Validation rules
            - Record types

## Step 2: Upload to Target Org
            Click **Upload** and select the connected org.
            The target org must be:
                * Connected (Deployment Settings enabled)
                * Same Salesforce instance (usually)
                * Under same production org family
---
## Step 3: Validate in Target Org (Production)
        Go to:
        > Setup → Deployment → Inbound Change Sets
        * Open the change set
        * You will get 3 button(Validate,Deploy,Delete)
        * Click **Validate**
            Validation checks:
                * Dependencies
                * Test classes (if Apex is included)
                * Deployment errors

What is Managed package tests
    Managed package tests are Apex test classes provided by third-party packages installed from AppExchange. These tests validate the package’s functionality,
    are not editable, and are usually excluded when running “Run Local Tests” during change set validation.  exmple- docSign          
 
 validation options
 1. "Run All Tests"-
     What it does : Runs every Apex test class in the org
                      Includes: Custom code, Managed package tests
 2. "Run Local Tests" :  Execute only the Apex test classes that belong to your org (custom code), excluding all managed package tests.
 3. "Run Specified Tests" : Runs only selected test classes
                            No Test Run (Sandbox Only)
                            🔹 What it does: Skips test execution completely
 
4. No Test Run (Sandbox Only) : Skips test execution completely
---
## Step 4: Deploy
        Once validation passes:
        * Click **Deploy**
        * Monitor deployment status
        ---
### ❌ Not Supported
        * Standard fields
        * Data records
        * Some standard picklist values
        * Connected app secrets
        * Users & roles

# 5️⃣ Dependencies in Change Sets
    One major concept is **Dependencies**.
    If you deploy:
    * A Custom Field that belongs to an Object
    * A Flow that uses another Flow
    * An Apex Class that references another class
        You must either:
        * Add dependencies manually
        OR
    * Click **View/Add Dependencies**
Failure to include dependencies causes deployment errors.
---
# 6️⃣ Test Coverage Requirement
        If Apex is included:
        * Minimum **75% code coverage** required in production
        * Tests must pass
        * You can choose:
        * Run All Tests
        * Run Specified Tests
        In production, Salesforce enforces strict testing before deployment.
---

# 7️⃣ Best Practices for Using Change Sets
    ✅ Always validate first
    ✅ Include permission sets
    ✅ Check dependencies carefully
    ✅ Test in Full/Partial Sandbox before Production
    ✅ Maintain release documentation
    ✅ Use naming conventions
    ---
# 8️⃣ Example Scenario

    Let’s say you created:

    * A Custom Object: `Project__c`
    * Custom Field: `Budget__c`
    * Flow: Project Approval Flow
    * Apex Trigger on Project

    You would:
    1. Add all components
    2. Add related permission sets
    3. Upload
    4. Validate in Production
    5. Deploy

# 9️⃣ Conclusion
Salesforce Change Sets are a powerful tool for admins and developers to manage metadata deployments between environments.
