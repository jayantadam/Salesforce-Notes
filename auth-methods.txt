1. Remote Site Setting
        A security whitelist in Salesforce that allows Apex to make HTTP callouts to an external endpoint.❗It does NOT store authentication details
        Purpose
            Allow outbound callouts to an external URL
            Prevent unauthorized data exfiltration
        Key Characteristics
            Only stores protocol + domain
            Required for Apex callouts (unless using Named Credentials)
            No credential management
            Hardcoded auth headers needed in Apex    

        Add into - Remote Site URL: https://api.example.com
        Example
            HttpRequest req = new HttpRequest();
            req.setEndpoint('https://api.example.com/data');
            req.setHeader('Authorization', 'Bearer ' + token);
            req.setMethod('GET');

what are the authentication methods in salesforce explain in detail
1. User Authentication (UI Access)
    1. Standard Login - Users log in with username and password through the Salesforce UI.
    2. Single Sign-On (SSO) - Users authenticate through an external identity provider (IdP) using SAML, OpenID Connect, or OAuth.
    3. Multi-Factor Authentication (MFA) - Requires users to provide additional verification (e.g., SMS code, authenticator app) for enhanced security.

2. API & Integration Authentication
    OAuth 2.0 is an authorization framework that allows applications to obtain limited access to user accounts on an HTTP service, such as Salesforce, 
    without sharing the user's credentials. It provides a secure and standardized way for applications to access resources on behalf of a user or themselves 
    (in machine-to-machine scenarios) by using access tokens.
                                                                        
    ✅ Core Concepts
    🔹 1. Connected App
            Acts as a bridge between external app and Salesforce
            Provides:
            Client ID
            Client Secret
    🔹 2. Access Token
            A temporary token used to:
            Call Salesforce APIs
            Example: HTTPAuthorization: Bearer 00Dxx0000000001!AQ0...``Show more lines
    🔹 3. Refresh Token
            Used to get a new access token when it expires
    🔹 4. Authorization Server
            Salesforce itself is the server issuing tokens
    🔹 5. Resource Server
            Salesforce APIs that the client wants to access
    🔹 6. Resource Owner
            The user or system that owns the data being accessed
    🔹 7. Client
            The external application requesting access to Salesforce data
    🔹 8. OAuth Flows   
            1. Authorization Code Flow (User-based)
            2. Client Credentials Flow (Machine-to-Machine)
            3. JWT Bearer Flow (Server-to-Server)
            4. Username-Password Flow (Legacy, not recommended)

        ✅ How OAuth 2.0 Works (General Flow)
                1. App requests access
                2. User logs into Salesforce (if required)
                3. Salesforce authenticates user
                4. Salesforce returns access token
                5. App uses token to call Salesforce APIs

    client - The application that wants to access the resource server on behalf of the resource owner. It can be a web application, mobile app, or server-side
            application.
    resource owner - Owns the data of resource server and grants access to client applications. It can be an end-user or an application that has control over 
                    the resources on the resource server. The resource owner is responsible for granting permission to the client application to access their 
                    resources on the resource server.
            example - a user who has an account on a social media platform (resource server) and wants to allow a third-party application (client) 
                    to access their profile information or post on their behalf.  
    authorization server - The server that issues access tokens to the client after successfully authenticating the resource owner and obtaining authorization.
                        It is responsible for validating the client's credentials and the resource owner's permissions before granting access.
            example - the social media platform's authentication server that verifies the user's credentials and issues an access token to the third-party application (client) 
                    after the user grants permission.               
    resource server - The API which stores the data and is accessed using the access token provided by the authorization server. It validates the access token 
                    and serves the requested resources to the client if the token is valid and has the necessary permissions.
            example - the social media platform's API server that hosts the user's profile information and allows access to it using the access token issued
                    by the authorization server.          

       OAuth 2.0 flow actors descending order of interaction:
        Authorization Server - The server that issues access tokens to the client after successfully authenticating the resource owner and obtaining authorization.
        Client - The application that wants to access the resource server on behalf of the resource owner.
        Resource Server -The API which stores the data and is accessed using the access token provided by the authorization server.   
        Resource Owner - Owns the data of resource server and grants access to client applications.

for authentication. grant_type can be:
    1. password (password flow) - used for user authentication where the client application directly collects the user's credentials (username and password) to obtain an access token. This flow is typically used for trusted applications where the client can securely handle user credentials.
    2. client_credentials (client credentials flow) - used for machine-to-machine authentication where the client application authenticates using its own credentials (client ID and client secret) without user involvement. This flow is suitable for server-to-server communication where the client application needs to access resources on behalf of itself rather than a user.
    3. authorization_code (authorization code flow) - used for user authentication where the client application redirects the user to the authorization server for authentication and authorization. After the user grants permission, the authorization server redirects back to the client application with an authorization code, which can be exchanged for an access token. This flow is commonly used for web applications and mobile apps that need to access resources on behalf of a user.
    4. JWT Bearer Token Flow: used for server-to-server authentication where the client application generates a JSON Web Token (JWT) and exchanges it for an access token.
         This flow is suitable for scenarios where the client application needs to authenticate without user interaction, such as backend services or scheduled jobs.
         
1. Authorization Code Flow (User-based)
            In Salesforce, Authorization Code Flow is used for secure OAuth-based integration where inbound uses Connected Apps for external access,
            and outbound uses Named Credentials to call external APIs without exposing credentials.
                ✔ Used for: Web applications
            🔹 Steps:
                        Redirect user to Salesforce login
                        User logs in & approves app
                        Salesforce returns authorization code
                App exchanges code for:
                        Access Token
                        Refresh Token
                where the client application (external system) redirects the user to Salesforce for authentication and authorization. After the user grants permission, 
                Salesforce redirects back to the client application with an authorization code. 
                
                🔁 Flow Overview (Authorization Code Flow)
                        Connected App configured in Salesforce
                        ✅ Redirect user to Salesforce login (authorize endpoint)
                        ✅ User logs in and grants access
                        ✅ Salesforce returns authorization code
                        ✅ Exchange code using client_id + client_secret
                        ✅ Receive access_token + refresh_token
                        ✅ Use access_token to call APIs

            login url: https://yourInstance.salesforce.com/services/oauth2/authorize?response_type=code&client_id=your_client_id&redirect_uri=https://www.getpostman.com/oauth2/callback&scope=full%20api%20refresh_token
                Send a POST request with application/x-www-form-urlencoded body:
                        POST https://yourInstance.salesforce.com/services/oauth2/token
                        Content-Type: application/x-www-form-urlencoded
                        grant_type=authorization_code
                        code=YOUR_AUTH_CODE
                        client_id=your_client_id
                        client_secret=your_client_secret
                        redirect_uri=https://www.getpostman.com/oauth2/callback

            The client application uses the access token to call Salesforce APIs on behalf of the user. If the access token expires, the client application can use the 
                refresh token to obtain a new access token without requiring the user to re-authenticate.
                    example of using access token to call Salesforce API:
                            GET https://yourInstance.salesforce.com/services/data/v59.0/sobjects/Account
                            Authorization: Bearer your_access_token
                                or 
                            POST https://yourInstance.salesforce.com/services/data/v59.0/sobjects/Lead/
                            Authorization: Bearer your_access_token
                            Content-Type: application/json

3.  Username–Password Flow
    In Salesforce, the Username-Password Flow is a legacy OAuth 2.0 flow that allows an application to obtain an access token by directly using the user's credentials
     (username and password). 

    This flow is not recommended for new integrations due to security concerns, but it can still be used in certain scenarios where other flows are not feasible.

      Connected App configured in Salesforce
            ✅ Send request with client_id + client_secret + username + password (+ security token)
            ✅ Salesforce validates credentials
            ✅ Receive access_token
            ✅ Use access_token to call APIs                  
  🔹 Steps:
            App sends username + password + client_id + client_secret to token endpoint
            Salesforce validates credentials
            Returns access token (no refresh token)

    Example using curl:
            curl https://login.salesforce.com/services/oauth2/token \
                -d "grant_type=password" \
                -d "client_id=YOUR_CLIENT_ID" \
                -d "client_secret=YOUR_CLIENT_SECRET" \
                -d "username=YOUR_USERNAME" \
                -d "password=YOUR_PASSWORD"
                response 
                {
                    "access_token": "00Dxx0000000001!AQwAQ...",
                    "token_type": "Bearer",
                    "issued_at": "1680000000000",
                    "instance_url": "https://yourInstance.salesforce.com"
                }

Named credentials in salesforce
    named credentials is a secure way to store and manage authentication credentials for external systems in Salesforce. It allows you to define the endpoint URL,
    authentication type, and credentials in one place, and then reference it in your Apex code or Flow without hardcoding sensitive information.

    To set up Named Credentials:
    1. Go to Setup → Named Credentials → New Named Credential
    2. Enter the following details:
    - Label: My External API 
    - Name: My_External_API
    - URL: https://api.external-system.com
    - Identity Type: Named Principal (or Per User if you want to use different credentials for each user)
    - Authentication Protocol: Choose the appropriate authentication method (e.g., Password Authentication, OAuth 2.0, etc.)
    - Enter the required credentials based on the chosen authentication protocol (e.g., username, password, client ID, client secret, etc.)

# 3️⃣ Inbound vs Outbound – Quick Comparison
                | Aspect        | Outbound                        | Inbound         |
                | ------------- | ------------------------------- | --------------- |
                | Config Object | Named Credential, Auth Provider | Connected App   |
                | OAuth Client  | Salesforce                      | External App    |
                | Token Stored  | Salesforce (Named Credential)   | External App    |
                | Auth Server   | External System                 | Salesforce      |
                | APIs Called   | External APIs                   | Salesforce APIs |

1. Outbound or callouts - The request is made from Salesforce org to an external system. 
   Concepts:
     i. Named Credentials / Remote Site Settings
     ii. External credentials 
     iii Rest API callouts (HTTP methods, authentication, etc.)

2. Inbound or call-ins - The request is made from an external system to Salesforce org. 
   Concepts:
     i.  Connected App
     ii.  Custom Apex REST API (@RestResource)
     iii. Authentication (OAuth, JWT, etc.)   

why we need to set up remote site settings for outbound callouts in Salesforce?
    Salesforce requires you to define Remote Site Settings to specify which external domains your Salesforce org can communicatete with. 
    This is a security measure to prevent unauthorized callouts to external systems. By setting up Remote Site Settings, you explicitly allow Salesforce to
    make HTTP callouts to the specified external URLs.
