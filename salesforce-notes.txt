1. if try block fails and we have some DML operation in finally block then will it roll back or not
    Now we are at the core of the trick: **you want to make sure the `finally` block can insert a record that is *not rolled back* even if the `try` fails**.
        **DML in `finally`** is **still part of the main transaction**, so it will roll back if the exception is unhandled.
        **To prevent rollback**, move the DML to a **separate transaction** using:
        * `@future` (simplest)
        * `Queueable` (more flexible)
        * **Platform Event** (for async logging)
        * Always **catch the exception** in `catch` to continue transaction if you want `finally` DML to succeed in the same transaction.

## 1. If exception is caught → finally DML can commit
     ```apex
        try{
            // ❌ This will fail (Name is required for Account)
            Account acc = new Account();
            insert acc;
        }catch (Exception e) {
            // ✅ Exception is handled
            System.debug('Error occurred: ' + e.getMessage());
        }finally {
            // ✅ This will execute and commit
            Contact con = new Contact(
                LastName = 'Final Contact',
                AccountId = acc.Id // Note: acc.Id will be null due to failed insert, but this is just for demonstration
            );
            insert con;
            System.debug('Contact inserted in finally');
        }
        ``
Result:
* `badRecord` fails
* `goodRecord` succeeds
-----------------------------------------------------------------------------------------------------------
## 2. If exception is NOT handled → everything rolls back
        ```apex
        try {
            insert badRecord;
        }
        finally {
            insert goodRecord;
        }
        ```
        Result:
        * exception propagates
        * entire transaction rolls back
        * `goodRecord` does NOT persist
-----------------------------------------------------------------------------------------------------------
## 3. Savepoint/Rollback matters too
If you do:
        ```apex
        Savepoint sp = Database.setSavepoint();
            try {
                insert badRecord;
            }
            catch(Exception e) {
                Database.rollback(sp);
            }
            finally {
                insert goodRecord;
            }
        ```
        Then:
        * rollback undoes work before rollback
        * `goodRecord` inserted after rollback can still commit
--------------------------------------------------------------------------------------------------------
Here’s a clear, interview-friendly approach.
    ## 1️⃣ Use `try-catch-finally` with a `@future` insert
    ```apex
    public class LogHelper {
        @future
        public static void insertLog(String logName) {
            Log__c log = new Log__c(Name = logName);
            insert log; // separate transaction → will not roll back
        }
    }

public class Demo {
    public static void demoMethod() {
        try {
            Account acc = new Account(Name='Test Account');
            insert acc; // suppose this fails
        }
        catch(Exception e) {
            System.debug('Caught exception: ' + e.getMessage());
        }
        finally {
            // This insert will run in a separate transaction
            LogHelper.insertLog('Finally block executed');
        }
    }
}

1. COUNT - Counts the number of related records (e.g., number of Contacts related to an Account).
2. SUM - Calculates the total of a numeric field across related records (e.g., total Opportunity Amount for an Account).
3. MIN - Finds the smallest value of a numeric field across related records (e.g., earliest Close Date of Opportunities related to an Account).
4. MAX - Finds the largest value of a numeric field across related records (e.g., latest Close Date of Opportunities related to an Account).

Stateful processing example in Batch Apex:
        public class BatchStatefulCheat implements Database.Batchable<sObject>, Database.Stateful {
            Integer success = 0;
            Integer failed = 0;
            public Database.QueryLocator start(Database.BatchableContext bc) {
                return Database.getQueryLocator('SELECT Id, Name FROM Account');
            }
            public void execute(Database.BatchableContext bc, List<Account> scope) {
                for (Account acc : scope) {
                    try {
                        acc.Name = acc.Name + ' - Updated'; // sample update
                        success++;
                    } catch (Exception e) {
                        failed++;
                    }
                }

                update scope; // bulk update
            }
            public void finish(Database.BatchableContext bc) {
                System.debug('✅ SUCCESS: ' + success);
                System.debug('❌ FAILED: ' + failed);
                // Optional: Notify user
                // send email / create log record
            }
        }

     SOQL -  Querying specific objects when you know where the data lives.
     SELECT Id, Name, Email FROM Contact WHERE LastName = 'Smith'

 SOSL (Salesforce Object Search Language)

    FIND 'Smith' IN ALL FIELDS RETURNING Contact(Id, Name), Account(Id, Name)

        | Feature    | SOQL                            | SOSL                   |
        | ---------- | ------------------------------- | ---------------------- |
        | Purpose    | Structured data query           | Text search            |
        | Objects    | One object (with relationships) | Multiple objects       |
        | Similar to | SQL                             | Search engine          |
        | Uses       | SELECT                          | FIND                   |
        | Best for   | Reports, filtered queries       | Global search features |

What is profile in salesforce and how to create a profile
A Profile in Salesforce is a collection of settings and permissions that define what a user can do within the Salesforce org. 
It controls access to objects, fields, tabs, and various system permissions. Every user must be assigned a Profile, which serves as their baseline level of access.
To create a Profile:
1. Go to Setup.
2. In the Quick Find box, type "Profiles" and select it.
3. Click "New Profile."
4. Choose an existing profile to clone (e.g., Standard User) and click "Next"
5. Enter a name for the new profile (e.g., "Custom Sales Profile").
6. Click "Save."

Salesforce Security Model (video 9 - 55.54 seconds)

1.Organization Level Security in Salesforce controls who can log in and from where. 
     It mainly includes Password Policies, Login IP Ranges, Login Hours, and Network Access.
2.Object-Level Security(OLS) (CRUD)  
  Controls access to entire objects like Account, Contact, Opportunity.  
  Managed through Profiles and Permission Sets.  
  Example: A user may have Read access to Accounts but no Delete access.
3. Field-Level Security (FLS)  
  Controls visibility and editability of individual fields within an object.  
  Managed through Profiles and Permission Sets.  
  Example: A user can view Account Name but not Revenue field.
4.  Record-Level Security (RLS)  
    Controls which records within an object a user can access.  
        1.  Organization-Wide Defaults (OWD)
              Sets the baseline access for all users on each object (e.g., Private, Public Read Only, Public Read/Write).
              Example: If Contacts are Private, users only see records they own (or those shared with them).
        2.  Sharing Rules
              Used to open up access beyond OWD. need to create public group first
              Types:
                  Owner-based: Share records owned by certain roles/groups.  - share records owned by sales team with marketing team.
                  Criteria-based: Share records meeting certain field criteria. - share accounts with Industry = 'Technology' with a specific group. 
        3.  Manual Sharing
              Record owner or admin can share a specific record with another user.
        4.  Teams
              Account Teams, Opportunity Teams, Case Teams allow sharing related records with team members.
        5.  Role Hierarchy
              Users higher in the hierarchy inherit access to records owned by users below them.
              Example: A Sales Manager can see records owned by their team.
        6.  Apex Managed Sharing
              Programmatic sharing for complex scenarios not covered by declarative sharing rules.  

4. Admin/Developer Controls:
     With sharing / without sharing in Apex controls whether sharing rules are enforced by code.
     Avoid granting View All or Modify All where possible — they bypass record-level controls.  
      
5. Other Org & Platform Security:
    Login & Session Controls: MFA, IP ranges, login hours, session timeout.
    Encryption & Data Protection: Shield Platform Encryption, encrypted fields.
    Auditing & Monitoring: Setup Audit Trail, Field History Tracking, Event Monitoring.
    Connected Apps & OAuth Policies: control external integrations and scopes.

Common Best Practices (Interview‑ready):
Principle of least privilege: give minimal object/field access needed.
    Use profiles for baseline, permission sets for additions.
    Set OWD to the most restrictive practical value (e.g., Private) then open via role hierarchy/sharing rules.
    Prefer public groups + criteria-based sharing over many manual shares.
    Enforce MFA and monitor with audit logs.
    Use Apex managed sharing for complex scenarios; test thoroughly for bulk operations and governor limits.

Short Example:
    OWD for Account = Private → Sales reps can only see owned accounts.
    Role Hierarchy: Sales Manager above reps automatically sees team accounts.
    Sharing Rule: all accounts with Industry = 'Enterprise' shared read/write with Marketing public group.
    Field‑Level Security: hide Salary__c from non‑HR profiles via FLS.
    Use a Permission Set to give an analyst API Enabled and extra object access without changing their profile.    

Hierarchy of Access  
            Profiles and Permission Sets → Field-Level Security → OWD → Role Hierarchy → Sharing Rules → Manual Sharing.
            Example  
            OWD for Account = Private → Users see only their own Accounts.  
            Role Hierarchy → Sales Manager sees team’s Accounts.  
            Sharing Rule → Share Accounts in “Enterprise” segment with Marketing.  
            Field-Level Security → Hide Revenue field from Marketing users.

Is permissoin set override the profile permissions
        No, Permission Sets do NOT override Profiles in Salesforce.
      Here’s the rule:
      Profiles set the baseline permissions for a user (object-level, field-level, app-level).
      Permission Sets can add extra permissions on top of what the Profile provides.
      Permission Sets cannot remove or reduce permissions granted by a Profile.

======================================================================TYPES OF RELATIONSHIPS IN SALESFORCE====================================================================================================================
✅ 1. Lookup Relationship
  Description: A loose association between two objects.
  Key Points:
    Child can exist without a parent.
    No cascade delete.
    No roll-up summary fields.
  Example: Contact linked to Account (but can exist independently). 
  **Important**==>   How many lookup relationship can create in one object ==> No fixed limit

✅ 2. External Lookup & Indirect Lookup
  Description: Used to link external objects (from external systems) to Salesforce objects.
  Key Points:
      External Lookup links external object to standard/custom object.
      Indirect Lookup links external object to Salesforce object using an external ID.

✅ 3. Master-Detail Relationship
  Description: A strong parent-child relationship.
  Key Points:
    Child record cannot exist without parent.
    Parent controls ownership, sharing, and deletion.
    Supports roll-up summary fields on the master.
  
  Example: Opportunity linked to Account (Opportunity cannot exist without an Account).
 **Important**==>  How many master detail relationship can create in one object ==> 2 

✅ 4. Many-to-Many Relationship
  Description: Achieved using a junction object with two master-detail relationships. we can reduce duplicate records with help of this

        One course can have many students.
  Key Points:
    Allows linking multiple records from two objects.
    Example: A student can enroll in multiple courses, and a course can have multiple students.

Delete Behavior of Junction Records in Many-to-Many Relationship
    junction records can delete from both the parents Student and Events
        Because the junction object uses Master-Detail relationships, its records are dependent on both parents.
        If either parent record is deleted, all related junction records are automatically deleted (cascade delete).
        The other parent remains intact, but loses the link because the junction record is gone.

 **Important**==>  why if Account record deleted then contact and oppportunites deleting?

The relationship between Account → Opportunity (and some other standard objects) appears as a Lookup relationship in the schema.

Salesforce has something called implicit cascade delete for certain standard objects(contact).

For Account → Contact, the platform automatically cascades the delete:

    From the UI, it shows a Lookup relationship for Contact, but in the backend, it works like a Master-Detail relationship because there is
    a standard Boolean field called CascadeDelete, and its default value is true.

For Account → Opportunity, Lookups don’t auto-delete:
        Normally, deleting an Account does NOT auto-delete Opportunities
        But they can be deleted if:
        You choose “Delete Account and Related Records”
        A Flow or Apex Trigger is configured
        Cascade Delete is enabled in Account Settings

lookup relationship - create a relationship to connects two objects loosely, allowing a child record to point to a parent record
 (like an Account to a Contact, or a custom object to a User) for data sharing, but the child can exist independently.
 it's defined on the child object by creating a new "Lookup Relationship" field, linking to the parent object, enabling easy data association
 without strict dependency or automatic deletion (unlike Master-Detail). 

Key Characteristics:
Loose Coupling: Child records aren't deleted if the parent is deleted (unless configured otherwise).
Optional: The lookup field on the child record doesn't have to be filled, allowing the child to exist without a parent.
One-to-Many: Typically links many child records to one parent record (e.g., many Contacts to one Account).
No Roll-Up Summaries: Cannot use Roll-Up Summary fields, which are a Master-Detail feature.
Creation: Created on the child object by selecting "Lookup Relationship" as the field type and choosing the parent object.

Types of OWD
          Organization-Wide Defaults (OWD) Types in Salesforce

          1.  Private  
              Users can only view and edit records they own or those shared with them. Most restrictive setting.

          2.  Public Read Only  
              All users can view all records, but only the owner or users with sharing can edit.

          3.  Public Read/Write  
              All users can view and edit all records. No ownership restrictions.

          4.  Public Read/Write/Transfer  
              Available for Leads and Cases. Users can view, edit, and transfer ownership of records.

          5.  Controlled by Parent  
              Used for child objects in a master-detail relationship. Access is inherited from the parent object’s OWD setting.

In Salesforce (specifically Apex), **access modifiers** control the visibility and accessibility of classes, methods, and variables. Here’s a plain text summary:
***
### **Access Modifiers in Salesforce Apex**

1.  **public**
    *   Accessible by any Apex code in the same namespace.
    *   Not automatically exposed to other namespaces or external apps.

2.  **private**
    *   Accessible only within the same class.
    *   Default modifier if none is specified.

3.  **protected**
    *   Accessible within the same class and its subclasses (inheritance).
    *   Useful for extending functionality in child classes.

4.  **global**
    *   Accessible everywhere, including outside the namespace (e.g., managed packages).
    *   Use with caution because it exposes code broadly.

5.  **webService**
    *   Used to expose methods as SOAP web services.
    *   Typically combined with `global` for external access.

6.  **testMethod**
    *   Special keyword for defining test methods (deprecated in favor of `@isTest` annotation).

***

### **Key Points**
*   **Classes** can be `public`, `private`, or `global`.
*   **Methods and variables** can use `public`, `private`, `protected`, or `global`.
*   **Default** for classes is `public` (within namespace), and for methods/variables is `private`.

Apex class contains
  An Apex class can contain **variables, constructors, methods, properties, inner classes, static blocks, and custom exceptions**.

An Apex class in Salesforce can contain the following components:
1.  **Class Declaration**  
    Defines the class name and access modifier.  
    Example:  
    `public class MyClass { }`

2.  **Variables (Fields)**  
    Instance or static variables to store data.  
    Example:  
    `public String name;`  
    `private static Integer count;`

3.  **Constructors**  
    Special methods to initialize objects.  
    Example:  
    `public MyClass(String n) { name = n; }`

4.  **Methods**  
    Functions that define behavior.  
    Example:  
    `public void displayName() { System.debug('Name: ' + name); }`

5.  **Properties**  
    Getter and Setter for encapsulation.  
    Example:  
    `public String Name { get { return name; } set { name = value; } }`

6.  **Inner Classes**  
    Classes defined inside another class.  
    Example:  
    `public class InnerClass { public void innerMethod() { System.debug('Inside inner class'); } }`

7.  **Static Initialization Blocks**  
    Code that runs once when the class is loaded.  
    Example:  
    `static { count = 0; }`

8.  **Interfaces and Implementations**  
    A class can implement interfaces.  
    Example:  
    `public class MyClass implements MyInterface { public void doSomething() { } }`

9.  **Exception Classes**  
    Custom exceptions can be defined inside a class.  
    Example:  
    `public class MyException extends Exception { }`

In short: An Apex class can contain variables, constructors, methods, properties, inner classes, static blocks, interface implementations, and custom exceptions.

what does it do in partial success
    **Partial success** happens when you use Database methods like `Database.insert`, `Database.update`, `Database.delete`, etc., with `allOrNone = false`.

    It means Salesforce will try to process each record one by one.  
    If some records are valid, they will be saved.  
    If some records have errors, only those records fail.  
    The successful records are still committed.
So:
    *   Good records = saved
    *   Bad records = failed
    *   No rollback of the entire operation
        Return detailed results for each record
        Every record gets a result object: isSuccess(),getId(),getErrors()
❌ Without partial success (allOrNone = true)
            If even one record fails:
            All records roll back.
            No DML is committed.
example
    List<Account> accs = new List<Account>{
        new Account(Name='Valid A'),
        new Account(Name=null),        // ❌ Missing required field
        new Account(Name='Valid C')
    };
Database.SaveResult[] results = Database.insert(accs, false);
