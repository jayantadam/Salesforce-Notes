In **Salesforce Lightning Web Components (LWC)**, *properties* are variables used to store data and control how components behave and communicate.
They are a core part of building dynamic UI in Salesforce.

# 🔹 Types of Properties in LWC
1. Public Properties (`@api`)
* Declared using the `@api` decorator
* Accessible from **parent components**
* Used for **component communication (parent → child)**

    ```js
    import { LightningElement, api } from 'lwc';

    export default class ChildComponent extends LightningElement {
        @api message;
    }
    ```
    👉 Parent can pass value:
    ```html
    <c-child-component message="Hello"></c-child-component>
    ```
---------------------------------------------------------------------------------------------------------------------------------------------
## 2. Private Properties
    * Default properties (no decorator)
    * Used **within the component only**
    * Not accessible outside

```js
name = "Salesforce";
```
---------------------------------------------------------------------------------------------------------------------------------------------
## 3. Reactive Properties
    * Properties that update the UI automatically when their value changes
    * In modern LWC, **all fields are reactive by default**
    * Earlier, `@track` was used
    1. Primitive types(string, number, boolean) are reactive by default.
    2. Objects and arrays are reactive when:
    - You reassign the entire object/array reference. example - ```js this.obj = { ...this.obj, name: 'alex' }```
    - Or use `@track` for deep reactivity (less common now).
    3. Getters are reactive when they depend on reactive properties.
    4. Wire properties are reactive when their parameters change.
    5. Template expressions are reactive when they reference reactive properties.
    6. Event handlers can trigger reactivity when they update reactive properties.  
```js
 count = 0;

handleClick() {
    this.count++; // UI updates automatically
}
```
------------------------------------------------------------------------------------------------------------------------------------------------
## 4. Tracked Properties (`@track`) *(less commonly needed now)*
* Used for **deep reactivity in objects/arrays**
```js
import { track } from 'lwc';
@track user = {
    name: 'John',
    age: 25
};
```
👉 Needed when modifying nested values:
``js
this.user.age = 26;
```
---------------------------------------------------------------------------------------------------------------------------------------------
## 5. Getter & Setter Properties

* Used to compute values dynamically
* Called automatically when referenced in template

```js
name = 'World';
get greeting() {
    return 'Hello ' + this.name;
}
set name(value) {
    this.name = value.toUpperCase();
}
```
```html
<p>{greeting}</p>
```
---------------------------------------------------------------------------------------------------------------------------------------------
6. Wire Properties (`@wire`)
* Used to connect to Salesforce data (Apex or LDS)
```js
import { LightningElement, wire } from 'lwc';
import getContacts from '@salesforce/apex/ContactController.getContacts';
export default class ContactList extends LightningElement {
    @wire(getContacts) contacts;
}
```

## 1. What is LWC and how is it different from Aura?
**Answer:**
Lightning Web Components (LWC) is a modern UI framework in Salesforce built using standard web technologies like HTML, JavaScript, and CSS.
It follows Web Component standards and runs on a lightweight engine.

**Key differences from Aura:**

* LWC uses native Web Standards; Aura is framework-based.
* LWC has better performance due to lightweight architecture.
* LWC uses one-way data binding; Aura supports two-way binding.
* LWC has simpler lifecycle hooks.
* LWC is more aligned with modern JavaScript (ES6+).

------------------------------------------------------------------------------------------------------------------------------------------------
## 2. Explain the LWC component lifecycle hooks.
**Answer:**
Important lifecycle hooks:
* constructor() – Component initialization.
* connectedCallback() – Runs when component is inserted into DOM.
* renderedCallback() – Runs after every render.
* disconnectedCallback() – Runs when removed from DOM.
* errorCallback(error, stack) – Handles child component errors.

In real projects, I mostly use connectedCallback for initial data load and renderedCallback carefully to avoid infinite loops.

------------------------------------------------------------------------------------------------------------------------------------------------
## 3. How does communication happen between components in LWC?
    **Answer:**
    There are three main ways:
    1. Parent to Child – Using @api decorator.
    2. Child to Parent – Using Custom Events. this.dispatchEvent(new CustomEvent('customEventNName', { detail: data }));
    3. Unrelated Components – Using Lightning Message Service (LMS) or Pub-Sub (older approach).

In enterprise apps, I prefer Lightning Message Service for cross-DOM communication because it's officially supported and scalable.

## 4. What are @api, @track, and @wire?
**Answer:**
@api
Makes a property or method public so it can be accessed by parent components.

@track
Earlier used to make properties reactive. Now, only required for nested objects/arrays (though reactivity has improved).

@wire
Used to connect LWC to Salesforce data (Apex methods or LDS). It provisions reactive data.

Example:

* @wire(getRecord, { recordId: '$recordId', fields: FIELDS })

## 9. How do you enforce security in LWC? or Explain LWC security layers in detail?
*To enforce security in Lightning Web Components (LWC), focus on both **Salesforce platform security** and **secure client-side coding practices**. 
Here are the main areas you should implement.

# 1. Apex security (Enforce CRUD & FLS in)
    LWC itself does **not automatically enforce** object permissions and field-level security when calling Apex.
    Always validate permissions in Apex controllers.
    ### Example
```apex
public with sharing class AccountController {
    @AuraEnabled(cacheable=true)
        public static List<Account> getAccounts() {      

        // Object-level check it will throw an error if user doesn't have access to Account object
        * `isAccessible()`- it will check if the user has access to the object
        * `isCreateable()`- it will check if the user can create records of the object
        * `isUpdateable()`- it will check if the user can update records of the object

        if (!Schema.sObjectType.Account.isAccessible()) {
            throw new AuraHandledException('No Account access');
        }

        * `WITH SECURITY_ENFORCED` - it will automatically check FLS and throw an error if user doesn't have access to any of the fields in the query.

            // Query with FLS enforcement it will throw an error if user doesn't have access to any of the fields
            List<Account> accs = [
                SELECT Id, Name, AnnualRevenue
                FROM Account
                WITH SECURITY_ENFORCED
            ];

        // Extra safety layer it will remove inaccessible fields and records for field and record-level security respectively,
         it will not throw an error but return only accessible data

        SObjectAccessDecision decision = Security.stripInaccessible(AccessType.READABLE, accs);
        
           List<Account> safeRecords = (List<Account>) decision.getRecords();
           List<Account> removed = (List<Account>) decision.getRemovedFields();

        return safeRecords;

    }
}
Use:
        * `Security.skltripInaccessible()`- it will remove inaccessible fields and records for field and record-level security respectively.
          AccessType options:
                    * `READABLE` - for read operations
                    * `CREATABLE` - for create operations
                    * `UPDATABLE` - for update operations

## 12. What are reactive properties in LWC?

**Answer:**
A property is reactive when:

    1. Primitive types(string, number, boolean) are reactive by default.
    2. Objects and arrays are reactive when:
    - You reassign the entire object/array reference. example - ```js this.obj = { ...this.obj, name: 'alex' }```
    - Or use `@track` for deep reactivity (less common now).
    3. Getters are reactive when they depend on reactive properties.
    4. Wire properties are reactive when their parameters change.
    5. Template expressions are reactive when they reference reactive properties.
    6. Event handlers can trigger reactivity when they update reactive properties.

## 1. How does LWC reactivity work internally, and what are common pitfalls?

**Answer:**

LWC uses a reactive membrane to track property changes. A component re-renders when:

* A reactive property used in the template changes.
* A new reference is assigned (for objects/arrays).

**Common pitfalls:**
* Mutating object properties without reassigning.
* Updating arrays using push() instead of creating a new array reference.
* Infinite loops triggered inside renderedCallback().

Correct pattern:
Instead of:
this.obj.name = 'New';

Use:
this.obj = { ...this.obj, name: 'New' };

---

## 2. Why does renderedCallback sometimes cause infinite loops?

**Answer:**
renderedCallback runs after every render. If you update a reactive property inside it,
it triggers another render, causing an infinite loop.

Fix:

* Use a boolean flag (hasRendered).
* Avoid updating tracked properties inside renderedCallback unless necessary.
* Move logic to connectedCallback when possible.

## 4. Explain the difference between shallow copy and deep copy in LWC and when it matters.

**Answer:**

Shallow copy copies references of nested objects.
Deep copy creates completely independent objects.

In LWC, shallow copy using spread operator works for most UI updates, but deep copy is required when:

* Modifying deeply nested structures.
* Avoiding unintended mutation side effects.

Deep copy example:
JSON.parse(JSON.stringify(obj)) (with limitations).

## 7. What happens when multiple @wire services are dependent on each other?

**Answer:**
Reactive parameters (with $) trigger re-evaluation.

Example:
    If wire B depends on result of wire A:
    * Wire A loads first.
    * When reactive property updates, wire B runs.

Pitfall:

* Undefined parameters can prevent wire execution.
* Need defensive checks.

Senior-level optimization:

* Chain logic carefully.
* Use imperative calls when dependency logic is complex.
