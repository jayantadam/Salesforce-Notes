4. If you don’t have object permission and record access and try to execute a SOQL query in Apex, the behavior depends on how the code is written.
    DML operations will succeed in all three types of classes (with sharing, without sharing, and inherited sharing) even if the user does not have object permissions,
    because Apex runs in system context by default and does not enforce CRUD permissions unless explicitly checked.
Types of User Context in Apex
        1. User Mode (Respect Sharing Rules)
        ✅ Applies in:
            Standard controllers
            Code declared with with sharing
            SOQL queries using WITH USER_MODE (newer feature)

            public with sharing class AccountService {
            public static List<Account> getAccounts() {
                return [SELECT Id, Name FROM Account];
                }
            }
        ✔ Behavior:
                Respects organization-wide defaults (OWD)
                Honors role hierarchy and sharing rules
                Enforces object-level and field-level security (if explicitly checked)
------------------------------------------------------------------------------------------------------------------------------------------------------------------------
        2. System Mode (Ignore Sharing Rules)
        ✅ Applies in:
                Triggers
                Classes declared without sharing
                Anonymous Apex
                Batch Apex, Queueable, Future methods (mostly system mode)

        public without sharing class AdminService {
            public static List<Account> getAllAccounts() {
                return [SELECT Id, Name FROM Account];
            }
        }
        ✔ Behavior:
            Ignores sharing rules
            Can access all records
            Does NOT automatically enforce FLS/CRUD (you must check manually)
------------------------------------------------------------------------------------------------------------------------------------------------------------------------
        3. Mixed Context
        Sometimes execution involves both modes.
        🧠 Example:
        A with sharing class calls a without sharing class
        → The called class runs without sharing

    Salesforce does NOT guarantee trigger execution order when multiple triggers exist on the same object.
👉 Result:
    One trigger updates field A
    Another trigger overwrites it
    Sometimes logic runs in different sequences
    Causes unpredictable results
✅ Goal
    ✔ Single source of truth
    ✔ Controlled execution order
    ✔ Maintainability across teams
    ✔ No duplicate / conflicting logic

            public class CaseTriggerHandler {
                private static Boolean isRunning = false;
                public static void run(
                    Boolean isInsert,
                    Boolean isUpdate,
                    Boolean isBefore,
                    Boolean isAfter,
                    List<Case> newList,
                    Map<Id, Case> oldMap
                ) {
                    // ✅ Recursion guard
                    if (isRunning) return;
                    isRunning = true;
                    if (isBefore) {
                        if (isInsert) {
                            beforeInsert(newList);
                        }
                        if (isUpdate) {
                            beforeUpdate(newList, oldMap);
                        }
                    }
                    if (isAfter) {
                        if (isInsert) {
                            afterInsert(newList);
                        }
                        if (isUpdate) {
                            afterUpdate(newList, oldMap);
                        }
                    }
                    isRunning = false;
                }
                private static void beforeInsert(List<Case> newList) {
                    CaseService1.beforeInsert(newList);
                    CaseService2.beforeInsert(newList);
                }

                private static void beforeUpdate(List<Case> newList, Map<Id, Case> oldMap) {
                    CaseService1.beforeUpdate(newList, oldMap);
                    CaseService2.beforeUpdate(newList, oldMap);
                }

                private static void afterInsert(List<Case> newList) {
                    CaseService1.afterInsert(newList);
                    CaseService2.afterInsert(newList);
                }

                private static void afterUpdate(List<Case> newList, Map<Id, Case> oldMap) {
                    CaseService1.afterUpdate(newList, oldMap);
                    CaseService2.afterUpdate(newList, oldMap);
                }

A batch job updates 5 million records daily. Business users complain about record locks. What optimization strategies will you implement?       
Record locks occur due to concurrent updates on the same records or parent relationships. I would reduce batch size, ensure ordered processing by parent,
 and avoid parallel execution. I would also partition data to avoid overlap, minimize unnecessary DML operations,
  and optimize triggers and flows. Additionally, I would implement retry logic for lock failures
   and move heavy operations to async processing to reduce contention. 
  
        Data Partitioning
            ↓
        Sequential Batch Execution (small size)
            ↓
        Ordered Queries (by parent)
            ↓
        Minimal DML
            ↓
        Async processing for heavy logic
✅ 1. Reduce Batch Size (VERY EFFECTIVE)
   Database.executeBatch(new MyBatch(), 50);// defualt 200
✅ 2. Avoid Parallel Batch Execution
    ✅ Fix:
    Run batches sequentially
    Avoid scheduling overlapping jobs
✅ 3. Partition the Data (IMPORTANT)
        Batch 1 → Accounts A–M
        Batch 2 → Accounts N–Z
        Or:
        By Region
        By CreatedDate
        By RecordType

✅ 3. Use Consistent Data Ordering
      SELECT Id, AccountId FROM Opportunity ORDER BY AccountId
    ✔ Why?
    Ensures records with same parent are processed together
    Avoids parallel threads trying to lock same parent
